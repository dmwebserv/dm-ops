## Brand & writing standards

Apply these to any client-facing content generated by any system (reports, emails, etc):

- **Never use em dashes or en dashes.** Standard hyphens (`-`) only.
- **Minimal, uncluttered design.** Avoid heavy branding/logo treatment in templates - a
  subtle accent (colour strip, not a wordmark) is enough.
- **Brand colour:** `#101513` (dark, near-black green) - matches the live site's theme colour.
- **Tone:** plain English, factual, warm but not fluffy. No vague marketing language.
- **Prefer scannable content over dense prose** - visual stats/summaries where possible
  rather than paragraph after paragraph of numbers already stated in text.
- **One-way communications should read as statements, not questions** - don't ask the
  client to choose between options in an automated, unsupervised message.

## Automation philosophy

- **Default to autonomous operation.** Systems should act without manual approval unless
  something is genuinely anomalous - don't default to "always ask" as a safety blanket.
- **Reserve human review for real anomalies only** - e.g. unusual data, thresholds crossed,
  thin sample sizes - not for routine, expected outcomes.
- **Testing should never require editing code.** Any system built should expose a test
  mode via config (YAML), so testing is a config flip, not a code change.

## Technical conventions

- **Client sites:** custom HTML/JS, not WordPress or a CMS - no plugin-patching concerns,
  but also no CMS-level automation hooks available.
- **Ops repo:** private GitHub repo `dm-ops`, used for both code and lightweight project
  tracking (via Issues).
- **Config pattern:** business-wide settings live under a `business:` key in `clients.yaml`;
  per-client settings live under `clients:`. Example: `business.test_mode`,
  `business.sender_name`, `client.contact_email`.
- **GitHub Actions permissions:** must be set to "Read and write" under
  Settings -> Actions -> General, or any workflow that commits/pushes will fail with
  exit code 128.
- **Sending domain:** `updates.dmwebservices.co.uk`, verified in IONOS DNS (SPF, DKIM,
  DMARC), used via Resend for outbound automated email.

## Lessons learned (common bugs, so they're not re-debugged from scratch)

| Problem | Cause | Fix |
|---|---|---|
| `git push` fails, exit code 128 | Actions has read-only repo permissions by default | Settings -> Actions -> General -> Read and write permissions |
| `IndentationError` around `main()` | Python is whitespace-sensitive; easy to break when pasting/editing | `if __name__ == "__main__":` block must be at column 0, with `main()` indented exactly 4 spaces under it |
| Uptime % misleadingly low/zero | Conflating "any flagged issue" (broken links, SSL warnings) with actual downtime | Only count unreachable/5xx errors as downtime; other flags are issues, not downtime |
| Resend 401 Unauthorized | Bad/stale API key, wrong permission level, or key regenerated without updating the secret | Regenerate a fresh full-access key in Resend, replace the GitHub secret exactly |
| Email renders with literal `**`/`#` characters | Naive `\n` -> `<br>` conversion doesn't render markdown | Use a real markdown-to-HTML renderer (`markdown` python package) before sending |
| GitHub web upload won't accept `.github/...` paths | OS file pickers treat dot-folders as hidden | Use "Add file -> Create new file" on GitHub.com and type the full path in the filename box - it auto-creates folders |
